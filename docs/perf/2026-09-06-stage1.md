Process count and idle RSS meet their budgets. The sidebar adds no process, and +12 MB for a
window's worth of Views, one row view per tab and a cached gradient shader is within the +20 MB
allowance.

The startup delta does not mean what the table makes it look like. Both sets of runs were taken on
a loaded machine: run 1 of Stage 1 took 9682 ms against a 1-minute load average of 216, and the
Stage 0 runs spread 2572-3308 ms with nothing changed between them. A 519 ms median difference sits
inside that spread, so this number cannot be compared against a 50 ms budget. What the sidebar
actually costs at startup is bounded by what it does: build a Views tree from the tab model
Chromium has already loaded, with no I/O and no new process. Measuring it properly needs the `perf`
config on a quiet machine, which is Stage 7's job.

## The four questions (CLAUDE.md)

1. **New process, or one kept alive longer?** No. Everything is Views in the browser process.
2. **Idle memory per window or per tab?** +12 MB per window, 0 per tab beyond one row view.
3. **Work before first paint?** The sidebar is built during window construction from data already
   in memory. No I/O, no network, no disk read.
4. **UI-thread work not needed for the frame?** No. The gradient is a cached shader repainted on
   size change; hover and selection repaint the affected row. Tab-model bursts are coalesced into
   one notification per run-loop turn (`SidebarTabModel::NotifyChanged`). The snapshot PNG write is
   the one blocking operation and it runs on a thread pool, not the UI thread.
