## Machine conditions during this run

Recorded first, because they bound what the numbers below can mean. The 1-minute load average
was 35 when the run started and 26 when it ended; the 15-minute average was 108 falling to 95, on
a 10-core M1 Pro. `mds_stores` (Spotlight) was the largest single consumer at 53% CPU, indexing
the external USB SSD that holds the Chromium checkout and `out/dev`. Zen, Steam and two Electron
apps were also running. This is a working desktop, not a quiet machine.

Idle RSS and process count survive that; startup does not. Section "Startup" below says so
plainly rather than reporting the noise as a regression.

## Against Stage 1

`docs/perf/2026-09-06-stage1.md`, same config, same method, same machine.

| Metric | Stage 0 | Stage 1 | Stage 2 | Delta vs Stage 1 | Budget |
|---|---|---|---|---|---|
| Process count | 9 | 9 | 9 | 0 | 0 extra processes |
| Idle RSS, all processes (MB) | 1490 | 1502 | 1473 | -29 | +20 MB per window |
| Startup to DevTools endpoint (ms) | 2630 | 3149 | 4439 | +1290 | +50 ms |

**Process count is equal to Stage 1 at 9**, in all three runs, and equal to the Stage 0 vanilla
baseline. This is the gate that matters and it is met: the whole Arc tab model — two stores, the
archive service, the tab search index, the folder tree — added no process. The archive is SQLite
opened on a background sequence inside the browser process, not a service.

**Idle RSS came out 29 MB *below* Stage 1.** Read that as "no measurable regression", not as a
29 MB saving: Stage 1's own three runs spread 1493-1511 MB and Stage 2's spread 1472-1504, so the
two distributions overlap and the medians differ by less than a single run's spread. What the
stage actually costs at idle is bounded by what it holds: entries are small structs in one store
per Chromium profile, shared by every window, plus one row view per visible row. Nothing per tab
beyond the row that was already there in Stage 1. A +0 to +30 MB reading is what that predicts,
and both the budget (+20 MB per window) and the measurement are consistent with it.

### Startup

The +1290 ms median delta does not mean what the table makes it look like, and this record does
not treat it as a regression. Both sets of runs have one slow outlier and a wide spread: Stage 2
measured 3085, 4439 and 8563 ms; Stage 1 measured 3031, 3149 and 9682 ms. The Stage 2 median
(4439) sits comfortably inside the Stage 1 range, and the Stage 1 median (3149) sits inside the
Stage 2 range. With three runs each and a 15-minute load average near 100, a median difference of
this size is noise, and comparing it against a 50 ms budget is not a meaningful operation.

Two structural facts bound the real cost better than this measurement can. First, the trace below
shows the whole Stage 2 persistence load — `ArciumProfileState`'s construction, which opens the
archive database, and `ModelStore::Load` — running on a `ThreadPoolForegroundWorker` at +128 ms
and finishing in 995 µs and 18 µs respectively, with a 3 µs reply on the UI thread. Second, the
sidebar's first rebuild after the model arrives costs 782 µs on the UI thread. Under 2 ms of
work total cannot produce a 1290 ms delta.

Measuring startup properly needs the `perf` config on a quiet machine, which is Stage 7's job
(R7.4 is where the budgets stop being advisory and start being a gate). Until then, per section 3
of the spec and CLAUDE.md, a perf result is discussed and recorded, not enforced.

## The four questions (CLAUDE.md)

Evidence for questions 3 and 4 comes from a startup trace, described in the section after this
one. Questions 1 and 2 come from the run above.

**1. Does it add a process, or keep one alive longer?** No. Process count is 9 in every run,
identical to Stage 1 and to the Stage 0 vanilla baseline. The archive is `sql::Database` opened on
a background sequence inside the browser process; the live model is JSON through
`ImportantFileWriter` on the same kind of sequence. Neither is a service, and Stage 2 opened no
WebUI surface — the plain archive list from Task 10 is Views, and Stage 6 is where a WebUI Library
replaces it.

**2. Does it add idle memory, per window or per tab?** Per window: nothing measurable (-29 MB
median, inside the run-to-run spread; see above). Per tab: nothing. The per-window addition is a
pointer to the shared store plus the row views for the rows a window actually shows. `ModelStore`
and `ArchiveService` are owned per Chromium profile through `ArciumProfileState`, not per window,
so a second window on the same profile adds views and no model. A Today row *is* a live tab and
carries no persistent record at all; a pinned or favourite entry is a small struct — an id, a
`space_id`, a URL, a title, an optional folder id and an order — well inside NF6's 1 KB per tab.

**3. Does it add work before first paint at startup?** Not on the UI thread. The trace puts
`ArciumProfileState`'s constructor (`arcium/browser/arcium_profile_state.cc:105`, which opens the
archive) and `ModelStore::Load` (`arcium/browser/model_store.cc:61`) both on
`ThreadPoolForegroundWorker` at +128.5 ms, costing 995 µs and 18 µs. The UI thread sees only the
reply: a 3 µs task at +927 ms. The sidebar therefore draws the live tab strip first and fills in
cold entries when the model arrives — a cold start paints without waiting for either file. This
matches R7.3's rule ahead of the stage that states it.

**4. Does it do UI-thread work that is not needed for the frame being drawn?** Some, and it is
worth naming rather than denying.

- *No blocking I/O.* No `ScopedBlockingCall` anywhere in `arcium/` appears on the UI thread's
  track. Details and the caveat in the tracing section below.
- *Notification coalescing.* `SidebarTabModel::NotifyChanged`
  (`arcium/ui/browser/sidebar_tab_model.cc:340`) ran five times across the 25 s trace, at 782,
  216, 115, 111 and 93 µs — 1.3 ms of UI-thread time in total, and a 782 µs worst case against an
  8 ms frame budget (NF4). One posted task per burst, as Stage 1 finding 5 requires.
- **The session-rebuild nudge is real UI-thread work.** Task 12 added a posted, coalesced
  `ResetFromCurrentBrowsers()` (`arcium/ui/browser/session_rebuild_nudge.cc`) after any
  entry-binding change, and `SessionServiceBase::BuildCommandsForBrowser` walks every window's
  every tab. It is coalesced to one posted rebuild per burst and it is off the frame being drawn,
  but it is not free and this record should not read as though it were. It cost nothing in the
  trace below **because nothing provoked it** — a nudge needs a pin, favourite or unbind, and no
  agent performs those (steps 2 and 3 of the close-out are the human pass). Its cost is bounded by
  Chromium's own periodic rebuild, which happens anyway every `kWritesPerReset` = 250 commands, so
  the nudge changes *when* that walk happens and not *whether* it does. Stage 2 findings 4 and 5
  carry the reasoning; how many nudges a normal pinning session provokes is on the human pass's
  watch list, and Stage 7 is where it gets measured rather than argued.

## Tracing, for question 4 — what was run and what it does and does not show

A2.3 asks for "no writes on the UI thread confirmed by the tracing script", and the task brief
suggested `--trace-startup=disabled-by-default-file` plus a check that no `base::ScopedBlockingCall`
appears on the UI thread's track. That recipe needed two corrections, recorded here so the next
person does not repeat them.

**The category is wrong.** `ScopedBlockingCall` emits `TRACE_EVENT_BEGIN("base", ...)` —
`base/threading/scoped_blocking_call.cc:44` — so it is in category `base`, not
`disabled-by-default-file`. Tracing only the suggested category produces an empty result that
looks like a pass. What was actually run:

```
out/dev/Arcium.app/Contents/MacOS/Arcium --user-data-dir=<fresh> --no-first-run \
  --no-default-browser-check --remote-debugging-port=0 \
  --trace-startup=base,toplevel,disabled-by-default-file \
  --trace-startup-file=<trace.json> --trace-startup-format=json \
  --trace-startup-duration=25 about:blank
```

**"No `ScopedBlockingCall` on the UI thread" is the wrong assertion.** The 25 s trace has 5808 of
them, 53 of which are on `CrBrowserMain`. Every one of the 53 is upstream Chromium's own, under
its `ScopedAllowBlocking` escape hatches during profile creation:

| Count | Source |
|---|---|
| 12 | `base/files/file_util_posix.cc` `PathExists` |
| 7 | `mojo/public/cpp/bindings/lib/interface_endpoint_client.cc` `SendMessageWithResponder` |
| 6 | `base/files/file_posix.cc` `Stat` |
| 6 | `ui/accelerated_widget_mac/window_resize_helper_mac.cc` `EventTimedWait` |
| 4 | `base/files/file_util_posix.cc` `DirectoryExists` |
| 4 | `base/files/file_util_posix.cc` `OpenFile` |
| 3 | `mojo/public/cpp/system/wait.cc` `Wait` |
| 3 | `net/disk_cache/blockfile/backend_impl.cc` `~BackendImpl` |
| 2 | `base/files/file_util_posix.cc` `CreateDirectoryAndGetError` |
| 2 | `base/files/file_util_posix.cc` `WriteFile` |
| 2 | `net/disk_cache/blockfile/in_flight_io.cc` `InvokeCallback` |
| 1 | `base/files/file_util_posix.cc` `MakeAbsoluteFilePath` |
| 1 | `chrome/browser/profiles/pref_service_builder_utils.cc` `CreateProfileReadme` |

**Zero are from `arcium/`.** So the assertion the check should make is "no `ScopedBlockingCall`
from Arcium code on the UI thread's track", and by that reading it passes. The only three
`arcium/` source locations anywhere in the trace are the two thread-pool loads and
`NotifyChanged`, all listed under question 3 and 4 above. The one UI-thread task whose source
mentions `sql/` is upstream's `components/blocklist/opt_out_blocklist/sql/opt_out_store_sql.cc`.

**A stronger, structural check backs this up.** `content::BrowserMainLoop` calls
`base::DisallowUnresponsiveTasks()` (`content/browser/browser_main_loop.cc:1089`), which calls
`DisallowBlocking()`, and `build/dev.gn` sets `dcheck_always_on = true`. Every `ScopedBlockingCall`
constructor runs `AssertBlockingAllowed()`. So in a dev build, blocking I/O from Arcium code on
the UI thread does not merely show up in a trace — it crashes the browser on the spot. The dev
build being usable at all is continuous evidence for NF5, and it does not depend on anyone
remembering to run a trace.

### What this trace does not show

Honest limits, so this is not read as more than it is:

- **The write path was never exercised.** The trace covers launch, 25 s idle and `about:blank`.
  Nothing pinned, favourited, renamed, foldered or archived, so `ModelStore`'s debounced write,
  the archive's row insert and the rebuild nudge produced no events. The argument that those are
  off the UI thread rests on the code, the `DisallowBlocking` DCHECK above and the unit suite, not
  on this trace. Confirming it under real use belongs to the human acceptance pass
  (`docs/stage2-findings.md`), and the trace is worth re-running during it with the same command.
- **First paint could not be anchored.** The three categories traced carry no paint or
  window-show marker, so "before first paint" above is argued from where the work ran
  (thread pool, +128 ms) rather than from a timestamp compared against a paint event. Adding
  `views` and `viz` categories would fix this; it was not needed to answer the question asked.
