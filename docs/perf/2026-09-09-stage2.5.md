# Stage 2.5 — Entry behaviour: performance

Stage 2.5 added nested folders and a schema migration. The four questions
below always apply and cost nothing to answer; the measured numbers are
discussed, never a gate.

## The measurement did not run, and why

`scripts/perf --runs 5 --label stage2.5` refused:

```
Arcium is already running from this out dir; quit it first
```

An `out/dev` Arcium (pid 19145) had been up for 6h44m at that point — the
traffic-light build from unrelated in-flight work, waiting on a visual check by
its owner. Killing it to obtain a number would have destroyed work nobody had
looked at yet, to produce a measurement that is explicitly not a gate. So the
number is missing on purpose, not by omission.

To take it, quit that instance and run:

```bash
scripts/perf --runs 5 --label stage2.5
```

The machine was otherwise quiet at the attempt (load 13.2, no siso). Earlier in
the same session it reached load **349** on ten cores, from an unrelated runaway
login shell at 99% CPU for seven hours and an Xcode build at 95% — worth knowing
before trusting any timing taken today.

Baseline to compare against, from `docs/perf/2026-09-07-stage2.md`: process
count 9, idle RSS 1473 MB, startup to DevTools endpoint 4439 ms (that startup
figure is itself noisy — its three raw runs were 8563, 3085 and 4439 ms).

## 1. Does it add a process, or keep one alive longer?

**No.** Nothing in this stage starts a process or opens a WebUI surface. The
folder tree is Views in C++ in the browser process, the migration runs on the
`ThreadPool` sequence `ModelStore` already owned to read the file, and no
surface was added that could keep one alive.

## 2. Does it add idle memory, per window or per tab?

**Per tab: nothing.** Folders are a side table over tabs; a tab gained no field.

**Per window: a few bytes per folder, and folders are counted in tens.** Each
`Folder` gained `std::optional<FolderId> parent_id`; each `SidebarFolder`
gained the same plus an `int depth`. `FolderId` is a `std::string` UUID, so an
engaged optional is one 36-character heap string — the small-string buffer does
not cover 36 bytes, so it is a real allocation, but only for folders that
actually have a parent. At a generous 50 folders all nested, that is under 4 KB
against a 20 MB per-window budget.

`BuildSidebarFolders` allocates per rebuild rather than per frame: a `std::set`,
a `std::map` of children, and four vectors sized to the folder count. They are
transient, not resident.

## 3. Does it add work before first paint at startup?

**A little, all of it off the UI thread and on a file already being read.**

The migration runs on the background sequence between the JSON parse and the
model — `ReadFileOnBackgroundSequence`, never `OnLoaded`. The v1→v2 step is
deliberately empty and returns true, so a v1 file costs one version stamp. The
deserializer's folder repair is two linear passes over the folders, each doing a
map lookup per parent link; at tens of folders it is microseconds.

**Unverified against the clock.** Item 3 is the one question here that wants a
measurement rather than an argument, and the measurement did not run. The
reasoning above says why it should be far below the +50 ms budget; it is not
evidence that it is.

## 4. Does it do work on the UI thread not needed for the frame being drawn?

Two paths worth naming, both bounded and neither near 8 ms.

**`folders()` → `BuildSidebarFolders`**, once per sidebar rebuild, not per
frame. O(folders log folders) for the sibling sort plus O(folders) for the
pre-order walk and the subtree-count rollup. The walk is an explicit stack, so
its cost is not the recursion depth. At tens of folders this is well under a
frame.

**`CanMoveFolderInTree`**, called from `CanDrop`, which fires on every pointer
crossing during a drag. It is O(folders) with **no allocation** — three linear
scans over the flattened list, matching the "asked again on every drag-move
event" contract that `IsOverHeaderAt` and `DropRowIndex` already state. At 50
folders that is 150 comparisons per move.

**Assumed counts:** tens of folders per space, hundreds of entries. Both paths
degrade linearly, so a user with a thousand folders would want the drag
predicate revisited; nothing else here would notice.

## What this stage did not measure

Startup, idle RSS and process count. All three want the run above on a quiet
machine with no `out/dev` Arcium alive.
