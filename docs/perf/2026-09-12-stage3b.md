**This run's scenario is a fresh, empty profile with no Arcium model file at all** — `scripts/perf`
launches `about:blank` in a brand-new `--user-data-dir`, so no space and no profile exists yet.
That is exactly the scenario the profile feature's own headline claim is about (a browser that has
never used profiles pays nothing for the code existing), and the numbers say it holds: process
count and idle RSS are unchanged from Stage 2 within noise, and startup is lower, not higher. It
is **not** a measurement of A3.3 (three spaces, two profiles, idle) or of a launch that restores a
tab into a profile — both need a seeded model and are the hand acceptance pass's job, not this
script's.

## The four questions, answered against what was measured and tested, not against the design doc's wording

1. **"A profile adds no process of its own while its spaces sit in the background, because a
   space with no loaded tab has no storage built and nothing to run."** The **conclusion** holds,
   proven by `ARestoredTabsProcessIsNotSpawnedUntilClicked`
   (`arcium/test/browser/profile_restore_browsertest.cc`): a restored tab's process host exists but
   is not initialised, and `RenderProcessHost::GetCurrentRenderProcessCountForTesting()` does not
   count it until the tab is activated. **The stated reason is wrong.** "No storage built" is false
   for a space with a *restored* tab: its profile's storage is built the moment session restore
   creates that tab's `WebContents`, not deferred until it is clicked. Only a profile with no
   restored tab at all builds nothing. This run's fresh profile has neither restored tabs nor
   profiles, so it cannot exercise this distinction; the browser test does.
2. **"Idle memory per window is unchanged; a loaded profile costs what its open pages cost, the
   same as those pages would cost anyway."** Contradicted for a profile with a restored tab: it
   pays for a network context and roughly seventeen storage contexts
   (`storage_partition_impl.cc:1391-1640`) at startup, before any page in it has "loaded" in the
   sense a user would recognise, so its cost is not the same as its pages' cost -- it is paid
   earlier and regardless of whether the tab is ever clicked. This run's own numbers are consistent
   with the *unused* case (no profile costs anything when none exists), which is a narrower claim
   than the sentence above states.
3. **"Startup does no more than before: the model file is read as it already was, and nothing asks
   for a profile's storage until a tab in it loads."** Contradicted, for the reason in (1): a
   restored tab's profile is asked for its storage at creation, during session restore, which is
   startup -- not deferred to the click. The model file read itself is unchanged (a short list
   added, per §12 of the stage design, corrected alongside this task).
4. **"Nothing new runs on the UI thread per frame; the removals and deletions are asynchronous, and
   the only added work per navigation is a string comparison in the guard."** Holds, by inspection
   of `arcium::IsInRightStorage` (`arcium/browser/profile_partition.cc`): a domain-string
   comparison plus, on the profile path, one `base::StrCat` to build the comparand -- still O(1)
   and off any I/O, matching the same "one comparison" shape Stage 2's report used for its own
   guard. `ClearArciumProfileData` and `DeleteArciumProfile`'s obliterate calls are asynchronous, as
   named in the design and unchanged by this task. Not independently re-traced this session; this
   line is accepted on inspection, not measurement, same as Stage 2.5 left its item 3 unmeasured
   and said so.

**Net correction:** two of the four claims as the brief phrased them are false for a profile with a
restored tab, and this note says so rather than adjusting the wording to fit. The feature's actual,
narrower promise -- proven above -- is that no profile costs anything until something in it is
either restored or clicked, and that even a restored profile's tab spawns no renderer process of
its own until it is clicked. "Nothing until a tab loads" was never true once restore is in the
picture; "nothing until a tab exists" is what the code delivers.
