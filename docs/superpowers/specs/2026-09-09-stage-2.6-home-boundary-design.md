# Stage 2.6 design: the pinned and favourite home boundary

Status: approved in the design session of 2026-09-09. Supersedes the "design
pending" placeholder in the master spec's Stage 2.6 section, and answers the
five open questions recorded there.

Research this design rests on: `docs/research/zen-home-boundary.md`, which
reads the rule out of Zen and Firefox and maps every clause onto Chromium
152.0.7977.83.

---

## 1. Goal

Navigating a favourite's or a pinned entry's tab away from its home does not
consume the entry. A link click that leaves opens a tab instead, and the
entry keeps showing what it was showing.

Both kinds are in scope. Zen reaches this by making an essential a pinned tab
(`tabData.pinned = tabData.pinned || tabData.zenEssential`); Arcium reaches it
by asking only whether a tab is bound to an entry, never which kind.

## 2. The rule

A navigation is **diverted into a new tab** when all of the following hold.
Otherwise it proceeds in the tab as normal.

1. It is in the **primary main frame** of a tab bound to a pinned or
   favourite entry.
2. `content::NavigationHandle::WasInitiatedByLinkClick()` is **true**.
3. `content::NavigationHandle::HasUserGesture()` is **true**.
4. It is not a reload and not a back/forward traversal.
5. The target URL is http or https and **has a host**.
6. The target host **differs from the host of the page currently loaded**,
   treating a leading `www.` as absent on either side.
7. **And** the target host **differs from the host of the entry's stored
   `TabEntry::url`**, same `www.` treatment.

Condition 2 is the whole policy on *which navigations count*. There is no URL
rule about redirects, scripted navigations or typed URLs, because none of them
set that bit: Blink classifies a navigation `kWebNavigationTypeLinkClicked`
only when a triggering event is present, and the only sources of one are
`<a href>`, SVG `<a>`, MathML `<a>` and form submits — and form submits are
classified `kWebNavigationTypeFormSubmitted` first. `location.href = …`,
`location.assign()` and `location.replace()` set none, **even inside a click
handler**. This is why an OAuth hop, a `<meta>` refresh, a server redirect, a
form POST, a typed URL and a session restore all stay in the tab, and why the
feature needs no allow-list of auth hosts and no heuristic.

Condition 3 exists because condition 2 alone is not enough: a programmatic
`anchorElement.click()` is still classified a link click by Blink, but it
carries no user gesture. See section 2.3 for why that distinction matters on
Chromium specifically.

Condition 4 is belt-and-braces. Blink classifies reloads and traversals
separately, so condition 2 already excludes them; Chrome's own
`TabbedWebAppNavigationThrottle` guards reloads explicitly, and matching it
costs one line.

### 2.1 Condition 7 is a deliberate divergence from Zen

Zen and Firefox compare the target only against the **currently loaded**
document's host. Condition 7 adds the entry's stored home host as a second
host that always keeps the click in the tab.

Why: it is strictly more forgiving. A click that Zen keeps in the tab is kept
here too, and condition 7 can only ever *prevent* a diversion, never cause
one. It fixes the case a host-only rule handles badly — a pinned
`mail.google.com` that has walked to `accounts.google.com`, where a link back
to `mail.google.com` would otherwise be torn out of its own pinned tab.

It is one clause of one function. Removing it, and the tests named for it,
restores Zen's rule exactly. That reversibility is the reason it is written
as a separate clause rather than folded into the comparison.

### 2.2 Consequences that are behaviour, not defects

- **Home moves with you.** Condition 6 measures from the page currently
  loaded, so a pinned `github.com` that has walked to `github.com/foo/bar`
  still treats `docs.github.com` as leaving. Confirmed by hand against Zen
  during the design session.
- **`target="_blank"` links never reach the rule.** They create a new
  `WebContents`, so the entry's tab sees no navigation at all. Same visible
  outcome, different mechanism.
- **The diverted tab has no boundary of its own.** It is a Today tab, bound
  to no entry, so the throttle never constructs for it. Clicks from there
  behave like ordinary Chrome.

### 2.3 Known divergences from Firefox, accepted

- **An iframe link with `target="_top"`.** Firefox requires an empty target,
  so a `_top` breakout is left alone. This design cannot see the target
  attribute: the navigation is a link click in the primary main frame, so it
  is diverted when the host differs. Accepted — the usual source is an
  embedded widget, and "an embed cannot replace your pinned tab" is the
  behaviour the feature exists to produce. Not worth an initiator-frame
  comparison.
- **Non-http schemes.** `mailto:`, `tel:` and custom protocols fail condition
  5, stay in the tab, and reach Chromium's external-protocol handling exactly
  as they do today.
- **A tab with no committed URL.** No current host, so only condition 7 can
  hold the click. Rare; the outcome is to divert, which is the safe one.
- **A scripted link click needs its own gesture check.** Firefox has no
  equivalent to condition 3, because Firefox's divert has nothing to do with
  the popup blocker. Chromium's does: the divert reopens the navigation with
  `WindowOpenDisposition::NEW_FOREGROUND_TAB`, which
  `components/blocked_content/popup_blocker.cc` treats as popup-blocking
  eligible in `ConsiderForPopupBlocking`, and that file's `ShouldBlockPopup`
  rejects any open with no user gesture outright
  (`if (!user_gesture) return PopupBlockType::kNoGesture;`). Without condition
  3, a programmatic `anchorElement.click()` — still a link click by Blink's
  classification, per condition 2, but never a user gesture — would be
  cancelled by this throttle and then silently eaten by the popup blocker: a
  navigation that would have proceeded in the tab without this feature simply
  never happens with it. Condition 3 removes the failure mode instead of
  papering over it, and costs nothing for the case the feature exists to
  serve, since a real link click always carries a gesture.

### 2.4 What a diverted click produces

A **new foreground tab in Today**, in the current space, with **no opener**.
Firefox's own test asserts `content.opener === null`, and inheriting an
opener would let the new page script the entry's tab. The entry's tab is
untouched.

Placement follows from the absent opener: Chromium's tab strip groups new
tabs next to their opener, and with none the tab appends to the end of the
strip, which is the end of Today. That is a consequence rather than something
this design sets, so A2.6.1 confirms it by hand rather than asserting it here.

Zen can route this into a Glance popup instead, behind a pref. Popup and
split modes are out of scope for this stage by the project owner's
instruction, so the spawned tab here is an ordinary tab.

### 2.5 The return affordance stays pinned-only

`can_return_to_pinned_url` is computed for `EntryKind::kPinned` only
(`arcium/ui/browser/sidebar_tab_model_entries.cc`). Zen's
`onLocationChange` returns early for essentials for the same reason: an
essential is meant to *be* its site. This design does not change that. It is
the single place the two kinds differ, and it already matches Zen.

## 3. Architecture

Three pieces. The logic lives in exactly one of them.

### 3.1 The rule, pure — `arcium/browser/model/home_boundary.{h,cc}`

```cpp
// True when a link click from `current` to `target`, in an entry whose
// stored home is `home`, should be pushed out of the tab.
bool LinkLeavesHome(const GURL& current, const GURL& target, const GURL& home);
```

No Chromium types, no tabs, no navigation. It lives in the `model` target,
whose only dependencies are `//base` and `//url`, so conditions 5, 6 and 7
are table-driven unit tests with no fixture. An empty `home` simply never
matches, which is the correct behaviour for an entry with no stored URL.

The `www.` allowance is a private helper in the `.cc`, shared by conditions 6
and 7 so the two comparisons cannot drift.

### 3.2 The adapter — `arcium/ui/browser/home_boundary_throttle.{h,cc}`

A `content::NavigationThrottle` modelled on
`web_app::TabbedWebAppNavigationThrottle`
(`chrome/browser/ui/web_applications/tabbed_web_app_navigation_throttle.cc`):
`MaybeCreateAndAdd(registry)` filters, `WillStartRequest()` decides.

`MaybeCreateAndAdd` returns without constructing unless the feature is on,
the navigation is in the primary main frame, and the tab is bound to an
entry. `WillStartRequest` reads `WasInitiatedByLinkClick()`, requires
`HasUserGesture()`, excludes reloads and traversals, and calls
`LinkLeavesHome`. To divert it builds
`OpenURLParams::FromNavigationHandle(...)`, sets
`WindowOpenDisposition::NEW_FOREGROUND_TAB`, clears `frame_tree_node_id`,
calls `WebContents::OpenURL` and returns `CANCEL_AND_IGNORE`.

**How it finds the entry.** Not through `BrowserView` or
`BrowserSidebarController`, but:

```
web_contents->GetBrowserContext()
  -> ArciumProfileState::GetForBrowserContextIfExists()
  -> binding()->EntryForTab(
         tabs::TabInterface::MaybeGetFromContents(wc)->GetHandle())
  -> model()->GetEntry(id)     // kind and stored url
```

Every step returns null or nullopt when it does not apply, so a prerender, a
tab mid-detach, a `WebContents` with no window, and a profile the sidebar has
never opened all fall out without a special case. The `IfExists` variant is
mandatory: the constructing variant posts an archive open and a model load,
and calling it from a throttle would start Arcium's disk I/O as a side effect
of any navigation in any profile. This is the same lookup the session-service
path already uses, and it reaches no window UI at all.

`//content/public/browser` is already a dependency of `arcium/ui/browser`, so
this adds no new GN dependency — only two filenames to `sources`.

### 3.3 The hook — `patches/0150-navigation-throttle-home-boundary.patch`

An include and one `MaybeCreateAndAdd` call in
`chrome/browser/chrome_content_browser_client_navigation_throttles.cc`,
beside where Chrome registers its own throttles. Two lines, no logic, with a
header naming the seam, the reason and the `arcium/` function it delegates
to, per the project's patch rule.

### 3.4 Feature flag

`BASE_DECLARE_FEATURE(kArciumHomeBoundary)` in
`arcium/common/arcium_features.h`, with an `IsHomeBoundaryEnabled()` accessor
matching `IsSidebarEnabled()`, checked once at the top of
`MaybeCreateAndAdd`. The project rule asks for a flag on anything
user-visible and new, and here it also makes "go back to Zen's behaviour" a
launch argument rather than a rebuild.

**Default: enabled.** The acceptance list exercises the shipped behaviour, so
the flag defaults on and `scripts/run --disable-features=ArciumHomeBoundary`
turns the boundary off for a side-by-side comparison. A flag that defaulted
off would make every acceptance item depend on remembering to pass a switch.

## 4. Testing

**Unit tests, `arcium/test/home_boundary_unittest.cc`** — the rule, as a
table. One named test per clause, including a test named for condition 7 so
that removing the divergence is a mechanical deletion.

**Unit tests, `arcium/test/home_boundary_throttle_unittest.cc`** — the
adapter's filtering. `//content/test:test_support` is already a dependency of
`arcium_unittests` and ships `content::MockNavigationHandle` and
`content::MockNavigationThrottleRegistry`, so primary-main-frame filtering,
the link-click bit, reload and traversal exclusion, and the unbound-tab case
are all testable without a browser.

**Not covered by tests:** throttle registration and the divert action
itself. This project has no browser-test target; those are verified by the
acceptance list below. That gap is stated rather than papered over.

## 5. Acceptance list

All executed by hand.

- **A2.6.1** Cross-host link click in a pinned tab opens a new foreground
  Today tab. The pinned tab is unchanged. `window.opener` is `null` in the
  new tab's console.
- **A2.6.2** A same-host link three levels deep stays in the tab; a link from
  there back to the entry's home host also stays. The second half is
  condition 7.
- **A2.6.3** A real Google sign-in from a pinned `mail.google.com` completes
  end to end without ever leaving the tab. This is the empirical confirmation
  the research document records as outstanding: the claim under test is that
  no OAuth hop arrives with `WasInitiatedByLinkClick()` true.
- **A2.6.4** A `target="_blank"` cross-host link opens one new tab, not two.
- **A2.6.5** Typing a cross-host URL into a pinned tab's URL pill navigates
  in place, and "Return to pinned URL" appears.
- **A2.6.6** A2.6.1 and A2.6.2 repeated on a favourite behave identically,
  except that no return affordance appears.
- **A2.6.7** A cross-host link click in an ordinary Today tab navigates in
  place. The boundary is opt-in.
- **A2.6.8** From a pinned `example.com`, a link to `www.example.com` stays
  in the tab.
- **A2.6.9** Quit, relaunch, click a cold pinned entry, then click a
  cross-host link: the boundary still applies. This proves the binding is
  re-established after restore.

## 6. Performance

The four questions, per the project's modus operandi.

1. **A process, or one kept alive longer?** No. The throttle is a plain
   object on the UI thread.
2. **Idle memory, per window or per tab?** None. The throttle exists only for
   the life of a navigation, and is constructed only for primary-main-frame
   navigations in tabs bound to an entry.
3. **Work before first paint?** None. Nothing runs until a navigation
   happens, and `GetForBrowserContextIfExists` never constructs profile state.
4. **UI-thread work not needed for the frame?** Two map lookups and a string
   comparison, inside a callback the navigation already makes. No I/O.

## 7. Out of scope

- **Glance / popup and split modes.** Ruled unnecessary for this stage by the
  project owner. A diverted click therefore becomes a full tab here, with
  none of Zen's cushion.
- **Making the boundary configurable per entry**, or an editable home set.
  Condition 7 already covers the case that motivated the idea.
- **Zen's folder rules.** The master spec (lines 216-221) records that Zen
  force-pins a tab entering a folder and strips its Essential status, and
  flags whether to follow as a Stage 2.6 question. **Decision: do not follow.**
  Arcium's nesting was built and accepted with kinds preserved, and having a
  drag silently demote a favourite would regress behaviour the project owner
  has already tested. Recorded here so the question is closed rather than
  rediscovered.

## 8. The five open questions, answered

The master spec's Stage 2.6 section recorded five. For the source evidence
behind each, see `docs/research/zen-home-boundary.md` section 4.

1. **What is "home"?** The host of the page currently loaded, plus the host
   of the entry's stored URL. Not an origin, not a registrable domain, not a
   user-editable set.
2. **Do auth and consent hops get an allowance?** They need none. They are
   not link clicks. No list, no heuristic.
3. **Does the boundary apply to pinned entries too?** Yes, to both kinds,
   identically. The spec's line 74 — free in-place navigation with a revert
   affordance — is the other half of the same behaviour, and Zen ships both
   together.
4. **Where does the new tab land?** A foreground Today tab in the current
   space, with no opener.
5. **What happens to the entry's own tab?** Nothing. The click does not land
   on it.
